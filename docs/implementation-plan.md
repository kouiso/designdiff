# FigDiff 全件解消・実利用検証計画

## 1. 目標と進め方

AI はリポジトリ URL から導入方法と機能を把握し、比較・原因調査・修正確認まで自律して進められる状態にする。desktop は、説明書を読まなくても人間が比較を完了でき、AI からも画面に即した案内ができる状態にする。

- 調査時点の open Issue 22 件・PR 2 件を対象にする。開始時と完了前に再取得する。
- 最新 develop から作業用 checkout を作る。既存作業と利用者の保存データを保護する。
- 「既存 Issue・PR 対応」「MCP dogfooding」「desktop dogfooding」を並行する。共有処理の変更は担当を一本化し、統合順序を管理する。
- 新規発見は再現条件・原因・既存修正と照合する。同じ問題は既存 Issue に集約し、未登録の問題だけ起票する。新規分も今回の修正対象にする。

## 3. MCP・desktop・共通設計の改善

**MCP の自律利用**

- README、API 資料、ツール説明を現行スキーマと一致させる。登録された全ツールを探索できるようにする。
- ローカルの個人スキルに依存しない新規 AI セッションで、導入・接続・対象探索・撮影・比較・詳細取得・再比較を通す。
- 比較対象と認証は利用可能な設定から探索する。取得できない情報は具体的に案内し、対象や資格情報を推測しない。
- 比較条件、失敗原因、復旧方法、停止理由を機械可読で返す。実装側を直すべき差分と、撮影・Figma 書出しの問題を区別する。

**説明書なしで使える desktop**

- 初回起動、認証、対象選択、画像取込み、比較、再比較、履歴・出力まで、次の操作が画面から分かる導線にする。
- 未実行・処理中・成功・失敗を区別し、エラーから入力を失わず復帰できるようにする。
- #118 の機能は、ノード詳細、トークン表示、除外領域編集、修正前後比較、アニメーション比較、問題報告、レポート保存として提供する。
- MCP の操作名をそのまま画面へ並べず、人間の作業目的に合わせる。AI の案内には実際の画面名・操作名を使う。

**SOLID と共有処理**

- 全7パッケージの責務・依存方向・重複を確認する。比較条件、座標変換、差分検出、採点、履歴保持の共通規則を共有する。
- 画像取得・デコード・保存・MCP 通信・Electron IPC・画面表示は、それぞれの実行環境の adapter に分ける。
- AI のループ制御や応答要約と、人間の選択・編集・確認操作は分離する。
- 既存の alignment 情報を拡張・再利用する。同じ入力と比較条件では、MCP と desktop が同じ比較領域・判定根拠を返す契約を設ける。
- 公開引数・保存形式は互換性を維持する。新規項目は原則任意とし、移行が必要な場合は既存データの読込みを検証する。

## 4. テスト仕様と実動確認

最初に `docs/test-specification.md` を作る。各ケースに対象機能、OS、前提、入力、操作、期待結果、独立した判定根拠、証跡、結果、関連 Issue を記録する。

| 検証群 | 必須シナリオ |
|---|---|
| 比較の正確性 | 同一画像、左右上下のずれ、1px／2px境界、局所欠陥併発、DPR・倍率・余白差、crop、mask、透明背景、長い画面 |
| MCP | 全登録ツールの成功・失敗、実 stdio／SDK 通信、初回導入、認証不足、権限不足、再起動、履歴保持、別作業の比較ループ |
| Electron | 実アプリの preload／IPC、認証保存、実 Figma 読込み、ファイル選択・D&D、全比較表示、編集・再比較・出力・再起動 |
| その他 | Chrome 拡張の実インストールと通信、Figma plugin の実起動・選択・書出し、動画比較、Android・iOS の対応撮影経路 |
| 実務利用 | Web・モバイル・複数プロジェクト、長い処理、日本語パス、ネットワーク失敗、過去証跡の再読込み、既存設定からの更新 |

- 正解は原画像、既知の座標、DOM 矩形、独立した画像検査から判断する。FigDiff 自身の一致率だけを合格根拠にしない。
- プレビュー上の位置と、実際に比較・採点した座標の対応も確認する。
- macOS を優先し、Windows と Ubuntu／WSL2 は `ssh windows-lan` 経由で検証する。Windows ネイティブと WSL の結果を分ける。
- build、lint、型検査、全テスト、既存 coverage 閾値、Playwright、独立画像検査、各 PR の CI を通す。
- 各変更をコードレビューし、統合後の実アプリで変更経路と隣接機能を再確認する。

## 5. 収束条件と残す成果物

- 修正 → 実利用 → 新規発見の照合・起票 → 修正を繰り返す。
- 最後の修正を含む同一リビジョンで、全機能の検証を **2巡連続、新規不具合0件** まで行う。途中で修正したら収束確認をやり直す。
- 確定した未解消不具合、失敗中の必須チェック、未検証項目がある間は、全完了とはしない。
- `docs/work-status.md` に Issue・PR・修正 SHA・検証証跡・残作業を対応付ける。
- Windows／WSL を実行できない場合は、失敗理由・実行コマンド・期待結果・証跡保存先を含む `handoff/windows-wsl-verification.md` を残す。未実行を成功扱いにしない。
- 完了報告には、解消した Issue・PR、OS別の実測結果、2巡分の証跡、外部対応が必要な残項を記載する。
